# 2026-11-27 最初の修正の検証

| 項目 | 値 |
|---|---|
| 上流基準 | `ef9292c`（`v2.11`） |
| 独自コミット | `299b24b` |
| 実行環境 | Linux x86-64、JDK 21.0.13（Temurin）、mml2vgm `mvcx64`（.NET 10） |

## 不具合

SFC『かまいたちの夜』のROMの曲データからメガドライブ版のBGMを作る作業で、mml2vgm が書いた XGM2 ファイルを
SGDK の `XGM2` 資源として組み込んだところ、**どの曲も1回鳴って止まった**。

`xgm2tool` は VGM を読んだときだけコマンド列に「ループ開始印」（`LoopStartCommand`）を入れ、XGC の書き出し・
曲の長さ・XD3 タグはすべてその印からループを読む。XGM ファイルはループを「最後のコマンド `$FF dddddd` の
アドレス」として持つが、それを印に戻す処理がないので、他のツールが書いた XGM2 のループは読み込み時に消えていた。

```
$ java -jar bin/xgm2tool.jar 318.xgm 318.xgc      # 修正前
XGM duration: 1982 frames (33 seconds) - loop: 0 frames (0 seconds)
```

## 修正

未圧縮の XGM を読んだ後に、ループのアドレスが指すコマンドへ印を付ける（`XGM.restoreLoopStarts()`）。
印を入れたら `updateTimes()` と **`updateOffsets()`** を呼び直す。後者を忘れると印の起点が 0 のままになり、
ループ区間を詰めるときの基準がずれて、**28曲中21曲が `max frame size reached at frame #0` で止まった**。

圧縮ずみの XGM は上流に「ループ点は復元できない」と注記があり、そちらは変えていない。

## 試験

| 確かめたこと | 結果 |
|---|---|
| mml2vgm の XGM2 のループが残る | 28曲すべて XGC になり、ループは5〜59秒（修正前はすべて0） |
| 同じ入力で曲の長さが変わらない | 318：33秒のまま、ループだけ 0 → 359 フレーム |
| VGM からの既定の経路が変わらない | 同じ `.vgm` から作った XGC が修正前後で**バイト一致** |
| ビルド手順の確認 | 修正前のソースから作った jar が、同梱の `bin/xgm2tool.jar` と同じ XGC を出す |

## 利用側での確認

[akiyan/kamaitachi-no-yoru-converter](https://github.com/akiyan/kamaitachi-no-yoru-converter) の
メガドライブ版で、ROMの曲データから作った28曲（`md_parts` → `rom_mml` → mml2vgm → XGM2）を
`XGM2` 資源として組み込み、ROM をビルドして鳴らした。 [作業の記録](https://github.com/akiyan/kamaitachi-ops/issues/88)

この修正で、XGM2 の**2本目のPCMを使う曲**（音源サンプルをそのまま鳴らす持続音と打音を別チャンネルに置く）も
ループしたまま組み込めるようになった。VGM 経由ではDACが1本しかなく、この構成は作れない。
